# 0006 订阅上下文与两类订阅的管理

日期：2026-10-02
状态：已采纳

## 背景

产品是订阅转换：既需要消费用户提供的外部订阅（上游），也需要对外提供转换后的订阅链接（下游）。在实现抓取、格式转换与公开分发之前，先把两类订阅的模型与管理 API 定下来，避免后续返工。

## 决定

新增 `crates/subscription` 订阅上下文，依赖 `user` 复用 `UserId`，依赖方向 `user ← subscription ← api`。一个上下文内两个聚合：

- `Source`（订阅源）：我们消费的外部订阅，管理名称、URL、启用状态
- `Publication`（发布订阅）：我们对外提供的订阅，管理名称、密钥、启用状态、过期时间，并通过 `publication_sources` 多对多绑定多个 `Source`（带排序）

本期只做管理 CRUD，不实现抓取、快照、格式转换、`/s/{secret}` 公开分发与格式字段；这些按后续增量推进。

具体取舍：

- **密钥明文存储**：`publications.secret` 明文落库，管理页可随时复制订阅链接。上游 URL 本身也含密钥且同样明文存储，威胁模型以 D1 访问权限为边界；若未来需要，再引入服务端密钥加密或一次性展示。
- **外键与索引**：与既有 schema 一致，`sources.user_id`、`publications.user_id` 加 `FOREIGN KEY` + 索引；`publication_sources` 对两端加 `ON DELETE CASCADE`，仓储删除源时再显式清理绑定，不依赖 PRAGMA 行为。主键继续用 TEXT UUID，D1 规模下相比整数键的差异可忽略。
- **删除语义**：删除订阅源即解除其在所有发布订阅中的绑定；删除发布订阅连带删除绑定行。

## 后果

- 管理 API 可独立交付和测试，抓取/转换/分发阶段只做增量迁移（新增 format、快照等列/表）
- 明文密钥意味着 D1 泄露即订阅链接泄露，与上游 URL 的暴露面一致，后续可单独立项收紧
- 两个聚合同库同上下文，绑定关系用数据库外键保证一致性；若未来拆分上下文，需要先摘除外键并改为应用层校验
