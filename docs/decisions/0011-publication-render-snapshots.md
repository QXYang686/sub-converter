# 0011 发布订阅的渲染快照缓存

日期：2026-10-03
状态：已采纳

## 背景

`GET /s/{secret}` 每次都要读取所有绑定源的原始 body（真实场景约 1 MB）、逐源解析 Clash YAML、合并去重再渲染。客户端会周期性拉取，这部分 I/O 与 CPU 被重复消耗，且与源快照大小线性相关。ADR 0010 已把节点/规则等结构化数据落库，但公开分发仍走原始 body。

## 决定

**物化渲染快照**

- 新表 `publication_snapshots(publication_id, format, content, userinfo_*, generated_at)`，主键 `(publication_id, format)`，外键级联删除；`format` 为将来多输出格式预留
- `GET /s/{secret}` 校验发布订阅启用/未过期后**直接查表**返回 `content` 与聚合 userinfo；命中时不再读取源 body
- 缓存未命中（首次创建、被失效后第一次拉取）时从当前源快照内联构建、写入表再返回，行为与原先一致；空配置语义不变

**重建与失效**

- 源刷新成功（含 304 补齐提取的 backfill）后：查 `list_by_source_id`，在同一个后台任务里重建所有绑定该源的发布订阅快照
- 管理变更即时失效（删除缓存行，不阻塞请求，下次拉取内联重建）：源的 URL 变更、启用状态变化、删除源、`PUT .../sources` 修改发布组合
- 源刷新失败/无数据不重建，保留旧快照；发布订阅的启用、过期、改名不影响已渲染内容（启用/过期在请求时实时判断，文件名取发布订阅名）
- 删除发布订阅由外键与显式批处理一并清理快照行

## 后果

- 常规拉取只查一张小表（几百 KB 的 content 行），不再读源 body、不再解析 YAML
- 内容最多滞后一次源刷新周期；管理变更后第一次拉取会做一次内联构建（一次性成本）
- 快照行大小受 D1 单行约 2 MB 限制，与源合并输出同量级；超出时应改为压缩存储或对象存储
- 未实现 TTL 与版本校验：重建依赖刷新触发与显式失效，若后台重建失败会在下次缓存未命中时自愈
